# CLEX MQTT

MQTT-брокер со встроенной веб-панелью управления.

Проект находится в разработке. Брокер поддерживает постоянные сессии и очереди, управление доступом, административную панель и пользовательские аккаунты. Подробнее – в [описании возможностей](docs/features.md).

Поддерживаются MQTT 3.1, 3.1.1 и 5.0. Для MQTT 5 доступны свойства сообщений, сроки хранения, совместные подписки и расширенная аутентификация SCRAM-SHA-256 с повторной проверкой в открытом соединении.

## Требования для разработки

- Rust 1.93.1 с rustfmt и Clippy.
- Node.js 22 LTS и npm. Они нужны для сборки панели и генерации миграций.
- PostgreSQL 17 с работающим локальным сервисом и утилитами `psql` / `createdb`.
- Python 3.10 или новее для вспомогательных команд.

На сервере запускается один исполняемый файл со встроенной панелью и SQL-миграциями.

## Локальный запуск

Из корня репозитория:

```bash
python3 scripts/local_setup.py
npm ci
npm run ui:build
cargo run -- migrate
python3 scripts/bootstrap_admin.py
cargo run -- serve
```

`local_setup.py` создаёт отдельную локальную роль PostgreSQL и базы `clex_mqtt_dev`, `clex_mqtt_test`, `clex_mqtt_codegen`, `clex_mqtt_shadow`. Для первоначальной подготовки ему нужен локальный доступ к PostgreSQL с правами создания ролей и баз. При повторном запуске существующие роли и базы сохраняются. По умолчанию `psql` подключается через локальный Unix socket; при необходимости задайте стандартные `PGHOST`, `PGPORT`, `PGUSER` и безопасный способ аутентификации PostgreSQL.

Случайные пароли сохраняются только в игнорируемом `.env` с правами `0600`. Имя администратора панели – `admin`; его пароль находится в `CLEX_ADMIN_PASSWORD` этого файла. `bootstrap_admin.py` передаёт пароль через stdin; существующая учётная запись сохраняется.

Адреса по умолчанию:

| Назначение | Адрес |
|---|---|
| Главная | http://127.0.0.1:8085/ |
| Администрирование | http://127.0.0.1:8085/admin |
| Личный кабинет | http://127.0.0.1:8085/account |
| MQTT TCP | 127.0.0.1:1883 |
| MQTT WebSocket | ws://127.0.0.1:8085/mqtt, subprotocol `mqtt` |
| Проверка готовности | http://127.0.0.1:8085/health/ready |

После входа создайте MQTT-пользователя и задайте ему отдельные фильтры публикации и подписки. Пустой список означает отсутствие разрешений. Учётные записи панели и MQTT-клиентов разделены.

Вход в веб-панели ограничен по IP. «Журнал действий» показывает успешные входы, отказы и ограничения с фильтрами и страницами. Для размещения за Nginx явно настройте доверенный адрес прокси и перезапись `X-Real-IP` по [руководству защиты входа](docs/deployment.md#защита-входа-и-журнал).

Client ID изолирован по MQTT-учётной записи. Например, `account-a` и `account-b` могут одновременно подключаться с Client ID `esp32-01`; у каждой пары собственная сессия и очередь. Повторное подключение с тем же пользователем и Client ID заменяет прежнее соединение этой пары. Доступ к общим топикам определяется ACL.

Раздел «MQTT-доступ» содержит вкладки «Учётные записи», «Группы» и «Проверка доступа». Группы задают общие правила MQTT для нескольких учётных записей. В форме группы доступны шаблоны наблюдения, телеметрии, управления и полного обмена относительно выбранного базового топика. Назначьте группу в форме учётной записи; её личные разрешения дополнят права активных групп. Явный запрет имеет приоритет над разрешениями. После изменения группы активные клиенты её участников пройдут повторное подключение. «Проверка доступа» показывает итог и правила для публикации, подписки или получения сообщения из конкретного топика.

Для клиента с поддержкой SCRAM укажите MQTT 5 и Authentication Method `SCRAM-SHA-256`. Клиент выполняет challenge/response и проверяет server-final из CONNACK. Включение готовности SCRAM происходит при создании или сохранении пароля пользователя, а для ранее созданной учётной записи – также после успешного MQTT-входа по логину и паролю. Форма учётной записи показывает доступные методы входа. Обычная аутентификация продолжает работать со всеми поддерживаемыми версиями MQTT. SCRAM использует пароль, подготовленный по SASLprep; готовность определяется полем API `scramReady`. Для внешних подключений используется TLS.

В разделе «Сообщения» вкладка «Поток» показывает принятые публикации с фильтрами по Client ID, MQTT-пользователю и топику, а вкладка «Retain» – последнее сохранённое значение каждого топика. Из карточки подключения можно перейти к сообщениям выбранного клиента. Поток обновляется каждые 2 секунды; доступны пауза, поиск содержимого и просмотр бинарного payload в Base64. В памяти процесса хранится до 1000 последних событий с бюджетом 8 МиБ и предпросмотром до 4 КиБ на сообщение; интерфейс показывает последние 500, начальная загрузка – до 100. При перезапуске брокера начинается новый буфер.

Вкладка «Диагностика» запускает сбор новых публикаций выбранного MQTT-пользователя, Client ID или топика на 1-300 секунд. После запуска отправьте сообщение и откройте его путь: ожидание блокировки хранилища, совпадения подписок, подготовка и фиксация очередей, ACL перед отправкой, PUBLISH и подтверждения получателя. Внутренний ID связывает входящий QoS 2 с PUBREL и исходящими доставками, включая повторную отправку после переподключения. QoS 0 показывает запись в соединение; QoS 1/2 – соответствующие ACK. Статус «Зафиксировано» относится к транзакции очередей; этапы получателя показаны в последовательности событий.

Сеанс диагностики общий для администраторов. В памяти процесса доступны до 100 публикаций, 128 событий на публикацию и 8 МиБ учтённого буфера; превышение отмечается в интерфейсе. Завершение сбора сохраняет просмотр результатов, новый сеанс и перезапуск процесса начинают свежую историю. Сбор охватывает новые публикации MQTT-клиентов и LWT; начальная выдача прежних Retain и входящие публикации мостов относятся к отдельным потокам. Для исходящих мостов отмечена граница локальной маршрутизации; дальнейший обмен виден в разделе «Мосты». Диагностика сохраняет метаданные обработки сообщения.

В строке MQTT-пользователя кнопка с отпечатком открывает «Сертификаты клиента». Загрузите один открытый сертификат PEM, выпущенный доверенным CA TLS-порта. Панель показывает SHA-256 отпечаток, срок действия и состояние. Для обновления сертификата сначала добавьте новый, переключите устройство, затем отключите или удалите старый. На пользователя доступно до 16 сертификатов. Переключатель «Требовать сертификат клиента» задаёт этот способ входа для всех его подключений; вход выполняется через MQTT TLS-порт. Закрытый ключ хранится на клиенте, а база брокера содержит отпечаток и открытые метаданные.

Для изменения интерфейса с горячей перезагрузкой запустите брокер и в другом терминале:

```bash
npm run ui:dev
```

Откройте http://127.0.0.1:5173. Vite проксирует `/api` на локальный сервер брокера. Секреты задаются в закрытом окружении серверной части.

## Личные кабинеты

Главная предлагает вход в личный кабинет и создание аккаунта, если регистрация включена. Административная панель доступна по `/admin`, пользовательский кабинет – по `/account`: регистрация, собственные MQTT-учётные записи, подключения и сообщения. Пространство `accounts/<логин>/` и квоты отделяют данные аккаунтов. Администратор управляет блокировкой, ограничениями и сбросом пароля кабинета. Регистрация включается явно через `CLEX_REGISTRATION_ENABLED=true`; по умолчанию она отключена. Подробности – в [docs/accounts.md](docs/accounts.md).

## Мосты между брокерами

Раздел «Мосты» соединяет этот брокер с удалённым сервером MQTT 5. Укажите адрес `mqtt://host:1883` или `mqtts://host:8883`, отдельную MQTT-учётную запись удалённого сервера и правила передачи. Для каждого правила выбирается направление, фильтр топиков и два префикса. Например, фильтр `sensors/#`, локальный префикс `workshop/` и удалённый `sites/workshop/` передают `workshop/sensors/temperature` в `sites/workshop/sensors/temperature`. Префиксы завершаются `/`; пустое значение сохраняет исходное начало топика.

Доступно до 16 мостов с 16 правилами в каждом. Передача выполняется с QoS 1; источники могут использовать QoS 0/1/2. Retain, двоичный payload, сроки жизни и свойства MQTT 5 сохраняются. Response Topic передаётся как исходное свойство; для request/response задайте согласованные пространства топиков на обеих сторонах. Начальные значения Retain отправляются при создании или включении моста. Очереди каждого моста ограничены `CLEX_MAX_PENDING` и `CLEX_MAX_PENDING_BYTES` и хранятся в PostgreSQL. При заполнении квоты публикация отклоняется целиком, включая её Retain и остальные доставки.

Пароли удалённых брокеров шифруются AES-256-GCM с отдельным ключом окружения `CLEX_BRIDGE_SECRET_KEY`. `local_setup.py` создаёт его вместе с новой конфигурацией. Для существующей локальной установки выполните `python3 scripts/bridge_key.py` и перезапустите брокер. Ключ сохраняется в закрытом `.env`; сохраняйте его вместе с резервной копией БД и используйте прежнее значение при обновлении сервиса. Панель показывает признак сохранённого пароля; при изменении адреса сервера или логина пароль назначается явно заново.

TLS проверяет имя сервера, срок действия и цепочку по системным CA либо открытым CA-сертификатам из формы моста. Отключение моста приостанавливает передачу и сохраняет текущую исходящую очередь; новые публикации попадают в остальные активные маршруты. Редактирование сохраняет уже назначенные топики очереди. Удаление моста удаляет его настройки и ожидающие отправки сообщения. Состояние подключения, очередь и счётчики видны в карточке; изменения записываются в журнал действий.

Проверка обмена между двумя локальными брокерами:

```bash
npm run test:bridges
```

Проверка использует два отдельных брокера со свободными loopback-портами и случайными схемами тестовой БД. Проверяются TCP/TLS, доверенный CA, двоичный обмен, Retain, восстановление исходящей и удалённой очередей и защита от циклов. Рабочий брокер продолжает обслуживать свои подключения.

## Мониторинг

Для просмотра графиков предусмотрены [панели Grafana](docs/monitoring.md#grafana): брокер, ресурсы сервера и резервные копии.

`GET /metrics` экспортирует метрики в OpenMetrics для Prometheus. Доступ включается переменной `CLEX_METRICS_TOKEN` и требует заголовок `Authorization: Bearer <token>`. Используется отдельный случайный токен длиной 32-256 URL-safe символов. Для существующей локальной конфигурации выполните `python3 scripts/metrics_token.py`, затем перезапустите брокер. Новая установка `local_setup.py` создаёт токен вместе с `.env`. Раздел «Система» показывает состояние мониторинга и путь метрик.

Экспорт включает подключения, пакеты, принятые и отклонённые публикации, объём MQTT-данных, сохранённые сессии, подписки, Retain, очереди по фазам QoS, мосты, пул PostgreSQL и гистограммы ожидания транзакции и COMMIT. Метрики содержат агрегаты; детализация клиентов и содержимого доступна административному API. Данные БД кешируются на 5 секунд; при ошибке `clex_mqtt_database_up` равен 0, а время последнего успешного снимка позволяет определить его возраст. Сбор ограничен двумя секундами и одной параллельной операцией.

Пример подключения и оповещений: [docs/monitoring.md](docs/monitoring.md). Токен хранится в закрытом окружении брокера и отдельном файле секретов Prometheus.

## Нагрузочные измерения

```bash
npm run bench:mqtt
npm run bench:mqtt -- --profile standard
```

Команда собирает release-бинарник, создаёт случайную схему в отдельной локальной `TEST_DATABASE_URL` и запускает собственный брокер на свободных loopback-портах. MQTT.js публикует двоичные payload и проверяет их получение каждым подписчиком. Отчёт содержит скорость публикации и доставки, p50/p95/p99, пропуски, повторы, порядок, повреждения, CPU и измеренный пик RSS процесса брокера. Процессы и схема завершаются при выходе; отчёт и снимок метрик сохраняются в игнорируемой `work/benchmarks`.

Для равномерной подачи используйте `--publish-rate`; значение `0` сохраняет пакетный режим. Параметры, границы измерения и сравнение результатов: [docs/benchmarking.md](docs/benchmarking.md).

## Проверки

```bash
python3 scripts/check.py
```

Команда проверяет Git-кандидаты на известные форматы секретов, собирает интерфейс, запускает rustfmt, Clippy и тесты брокера, включая PostgreSQL-интеграцию. Для неё обязателен отдельный `TEST_DATABASE_URL`, отличный от `DATABASE_URL`. Каждый тест создаёт случайную схему в выделенной тестовой базе и удаляет собственную схему после успешного завершения.

Обычный `cargo test` запускает автономные проверки; PostgreSQL-тесты помечены как требующие окружение. Полный путь проверки – `scripts/check.py`.

Проверка запущенного сервиса независимым MQTT.js-клиентом:

```bash
npm run test:mqtt
```

Скрипт использует локальный `.env`, создаёт ограниченную тестовую MQTT-учётную запись и проверяет TCP/WebSocket. В сценарии совместных подписок два MQTT 5 обработчика получают сообщения одной группы по очереди, а обычный подписчик получает каждое сообщение. Затем проверяется работа оставшегося участника после выхода второго из группы. После проверки скрипт удаляет тестовые retained-значения и отключает свою учётную запись, оставляя её для аудита. Журнал проверки содержит результаты операций.

Проверка SCRAM выполняется независимым MQTT.js-клиентом с расчётом PBKDF2/HMAC через Node.js crypto: проверяются challenge, подпись сервера и бинарный обмен QoS 2. Протокольные тесты отдельно проверяют повторную аутентификацию, ошибочные последовательности, отзыв доступа и таймауты.

Для совместной подписки укажите в MQTT 5 клиенте фильтр `$share/workers/sensors/#`. Участники с одинаковым фильтром разделяют входящие сообщения. В разрешениях подписки MQTT-пользователя задайте внутренний фильтр `sensors/#`. Разные имена групп или внутренние фильтры создают отдельные группы.

Дополнительная проверка MQTT через TLS включается парой `CLEX_SMOKE_TLS_URL` и `CLEX_SMOKE_TLS_CA_FILE`. Для локального сертификата со сроком действия один день остановите предыдущий экземпляр сервера и запустите:

```bash
python3 scripts/dev_certificate.py
CLEX_TLS_ADDR=127.0.0.1:8883 \
CLEX_TLS_CERT_FILE=certs/development/localhost.pem \
CLEX_TLS_KEY_FILE=certs/development/localhost.key \
cargo run -- serve
```

В другом терминале:

```bash
CLEX_SMOKE_TLS_URL=mqtts://127.0.0.1:8883 \
CLEX_SMOKE_TLS_CA_FILE=certs/development/localhost.pem \
node scripts/smoke.mjs
```

Эта проверка использует ту же временную учётную запись и отдельный топик `/tls`, проверяет бинарный обмен с QoS 1 и Retain=0 и доверие к серверу по указанному CA. Проверка сертификата остаётся обязательной; локальный сертификат предназначен только для разработки.

Сквозная проверка mTLS:

```bash
npm run test:mtls
```

Команда запускает отдельный процесс брокера на свободных loopback-портах и использует случайную схему `TEST_DATABASE_URL`. OpenSSL создаёт временный CA, серверный и клиентские сертификаты. Проверяются три режима TLS, вход MQTT 3.1/3.1.1/5, передача сообщений, ACL, привязка к пользователю, неверный CA, истёкший сертификат, ротация и отзыв, CSRF административного API и защита открытия сессии. Временный процесс, схема и ключи удаляются после проверки; работающий экземпляр разработки продолжает обслуживать свои подключения.

Проверка панели в headless Chromium:

```bash
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npx playwright install chromium --only-shell
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:ui
```

Перед запуском передайте учётные данные отдельного локального администратора через `CLEX_UI_TEST_USERNAME` и `CLEX_UI_TEST_PASSWORD`. Создать его можно командой `cargo run -- admin create --username ui-check --password-stdin`, передав пароль через stdin. Браузерная проверка получает учётные данные из переменных окружения и работает с loopback-адресом; адрес задаётся `CLEX_UI_BASE_URL`, по умолчанию `http://127.0.0.1:8085`. При необходимости путь к установленному Chromium задаётся `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

Скрипт проверяет реальный вход и выход, разделы панели, форму MQTT-учётной записи, ошибки браузера и горизонтальное переполнение на экранах 1440 × 1000 и 390 × 844. Снимки сохраняются в игнорируемой папке `work/ui`. После проверки удалите временного администратора. Храните его пароль в закрытом окружении проверки.

Отдельная проверка интерфейса сообщений с изолированными ответами API:

```bash
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:messages-ui
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:diagnostics-ui
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:access-ui
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:certificates-ui
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:bridges-ui
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npm run test:monitoring-ui
```

Проверяются 24 источника, одинаковые Client ID разных пользователей, фильтры, пауза, предел событий, очистка списка, смена процесса, Retain и мобильный вид. Проверка использует файлы интерфейса локального брокера и тестовые ответы API; рабочая база сохраняет своё состояние.

Проверка доступа охватывает создание группы по шаблону, разрешения и запреты, назначение группы пользователю, фильтр участников, объяснение решения ACL, отключение и удаление группы, а также мобильную форму. Серверные проверки этих операций выполняются в изолированной тестовой PostgreSQL.

Проверки жизненного цикла входят в `scripts/check.py`: отдельный процесс брокера, защита от второго экземпляра на той же базе, восстановление offline QoS 1 и обоих направлений QoS 2 после SIGKILL, остановка при потере соединения с блокировкой и завершение по SIGTERM. Для QoS 2 через совместную подписку проверяются продолжение входящего обмена после PUBREC с однократной рассылкой и повтор исходящего PUBREL с прежним Packet Identifier. Дополнительно проверяется завершение процесса в настроенный срок при намеренно заблокированной фоновой транзакции. Проверки используют отдельную схему тестовой БД.

## Миграции

Источник схемы – `db/schema.prisma`. SQL генерируется официальным Prisma CLI в отдельной базе разработки:

```bash
python3 scripts/generate_migration.py descriptive_change
```

Сгенерированные `db/migrations/*/migration.sql` сохраняются с исходными контрольными суммами. Изменения схемы оформляются новыми миграциями через `scripts/generate_migration.py`. Брокер применяет миграции отдельной командой `migrate` через SQLx с проверкой контрольных сумм и блокировкой применения.

```bash
cargo run -- migrate
```

На время миграции брокер должен быть остановлен. Перед изменением production-БД нужна проверенная резервная копия.

## Развёртывание

Для нового сервера начните с [пошаговой подготовки VPS на Ubuntu 24.04](docs/ubuntu-vps.md): выбор конфигурации, DNS, SSH-ключ и отдельный SSH-порт.

Сборка бинарника со встроенной панелью:

```bash
npm ci
npm run ui:build
cargo build --release --locked
```

Конфигурация задаётся окружением. Примеры конфигурации находятся в `.env.example` и `.env.production.example`. Инструкции и шаблоны Nginx, systemd и Docker: [docs/deployment.md](docs/deployment.md).

Устойчивые данные сохраняются транзакциями до соответствующего MQTT-подтверждения. Для PostgreSQL обязательны `fsync=on`, `full_page_writes=on` и синхронная фиксация.
