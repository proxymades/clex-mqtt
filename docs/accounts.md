# Личные кабинеты

Главная `/` содержит вход в личный кабинет и ссылку на создание аккаунта, если регистрация включена. Кабинет пользователя доступен по `/account`, административная панель – по `/admin`. Аккаунт человека, административная учётная запись и MQTT-учётные записи разделены.

## Включение регистрации

Регистрация отключена по умолчанию. В конфигурации сервиса задайте:

```dotenv
CLEX_REGISTRATION_ENABLED=true
CLEX_MAX_ACCOUNTS=100
```

После изменения конфигурации перезапустите сервис. Отключение регистрации сохраняет вход существующих пользователей. Общий предел учитывает активные и заблокированные аккаунты; диапазон – 1-1000.

Для production требуется HTTPS с корректным `CLEX_PUBLIC_URL`. Регистрация использует логин и пароль. Восстановление доступа выполняет администратор через сброс пароля аккаунта.

## Первая MQTT-учётная запись

1. Выберите «Создать аккаунт» на главной странице или откройте `https://mqtt.example.com/account/register`.
2. Укажите логин из 3-32 латинских букв, цифр, `_` или `-`; регистр букв не различается. Пароль проверяется сервером на длину 12-256 байт.
3. В разделе «MQTT-доступ» нажмите «Добавить учётную запись» и задайте название и отдельный пароль.
4. Скопируйте показанный MQTT-логин в настройки устройства. Название используется внутри кабинета; MQTT-логин имеет формат `<логин аккаунта>.<название учётной записи>`, например `alex.esp32-01`. Логин аккаунта и название MQTT-учётной записи закрепляются при создании.
5. Укажите адрес брокера и TLS-порт из кабинета. Проверяйте сертификат и имя сервера.
6. Добавляйте показанный префикс пространства ко всем MQTT-топикам.

Логин аккаунта уникален и не переименовывается. Каждый аккаунт получает неизменяемое пространство `accounts/<логин>/`. Например: `accounts/alex/sensor/temperature`.

После префикса задавайте собственную структуру топиков. Например: `accounts/alex/temperature` или `accounts/alex/room/light`.

Адрес брокера, TLS-порт, префикс и полный пример топика копируются отдельными кнопками. MQTT-логин копируется из таблицы учётных записей. Client ID задаётся на устройстве и появляется в разделе подключений после соединения.

В форме учётной записи указываются полные MQTT-фильтры: `accounts/alex/sensor/#` разрешает эту ветку, `accounts/alex/#` – все топики аккаунта. На устройстве и в разрешениях используется один и тот же полный топик. Пустое поле запрещает действие. Сервер сохраняет указанные фильтры и проверяет границу аккаунта при публикации, подписке, доставке, Retain и Will. Для короткого фильтра или префикса другого аккаунта API возвращает ошибку.

Одна MQTT-учётная запись может использоваться несколькими устройствами или приложениями. У каждого одновременного подключения должен быть свой Client ID. При совпадении MQTT-логина и Client ID новое соединение заменяет прежнее. Общая запись означает общий пароль и права; её отключение затрагивает все использующие её клиенты. Для независимого управления доступом создавайте отдельные записи.

## Возможности кабинета

- Создание, включение, отключение и удаление своих MQTT-учётных записей.
- Смена MQTT-паролей и разрешений на публикацию и подписку.
- Просмотр своих подключений и сохранённых сессий, отключение активного клиента.
- Просмотр сообщений своего пространства и удаление своих Retain.
- Просмотр квот и смена пароля аккаунта.

Изменение MQTT-пароля или разрешений отключает активные клиенты этой учётной записи для повторной аутентификации. Удаление учётной записи удаляет её сессии, подписки и очереди; Retain остаётся в пространстве аккаунта.

Смена пароля аккаунта завершает его веб-сеансы. Пароли MQTT-учётных записей сохраняются. Для аккаунта доступно до 10 веб-сеансов сроком до 8 часов каждый.

Поток сообщений показывает новые публикации сверху и использует общий просмотрщик с административной панелью: пауза и продолжение обновления, очистка списка на экране, поиск, подробности, копирование топика и содержимого. Очистка списка сохраняет сообщения в буфере брокера и Retain. Пользователь получает до 100 последних сообщений своего пространства с непрозрачными случайными ключами для локального списка; глобальные ID и курсоры потока не выдаются. Буфер предпросмотра очищается при перезапуске.

## Квоты

| Ограничение аккаунта | По умолчанию |
|---|---:|
| MQTT-учётные записи | 10 |
| Одновременные подключения | 10 |
| Сохранённые MQTT-сессии | 100 |
| Обязательства хранения сообщений | 1000 |
| Учтённое содержимое хранилища | 8 МиБ |
| Новые принятые публикации за секунду | 20 |

Общий бюджет хранения учитывает доставки всех устройств, входящий QoS 2, Retain, Will и исходящие очереди мостов для сообщений аккаунта. Каждое обязательство учитывается отдельно. В размер входят payload, топик и JSONB-свойства; это прикладная квота, а не точный размер файлов PostgreSQL. Общие ограничения брокера продолжают действовать.

Когда у сообщения аккаунта не остаётся долговечных ссылок, его содержимое очищается. Компактная запись ID операции сохраняется для согласования повторов в пределах существующего периода до часа. Она не содержит прежних payload, топика, свойств и идентификатора клиента. Такие записи не входят в бюджет очередей; их время жизни и скорость создания ограничены. Сообщения без владельца сохраняют прежний порядок хранения.

Повтор уже принятого входящего QoS 2 и повтор внутреннего ID операции не расходуют лимит новых публикаций повторно. Бюджет публикаций использует секундные интервалы часов PostgreSQL и сохраняется в БД. Он ограничивает новые принятые сообщения, а не каждый сетевой пакет.

Уменьшение квот сохраняет ранее принятые долговечные обязательства. Новые записи ограничиваются до освобождения места. Прежняя пара MQTT-пользователь/Client ID может заменить свою сессию в пределах лимита; новые идентификаторы дополнительно ограничиваются числом сохранённых сессий.

## Администрирование

В разделе «Аккаунты» администратор может заблокировать аккаунт, изменить его квоты и назначить новый пароль аккаунта. Блокировка отзывает веб-сеансы и закрывает MQTT-подключения. Очереди и Retain сохраняются; отложенный Will ждёт повторного включения аккаунта и не блокирует обслуживание остальных пользователей.

После изменения настроек аккаунта его активные MQTT-клиенты переподключаются. Сброс пароля аккаунта сохраняет MQTT-пароли; новый пароль аккаунта передаётся пользователю безопасным способом.

Пользовательские сеансы не дают доступа к административным API, группам, мостам, общей диагностике и системным настройкам. MQTT-правила и группы не расширяют пространство учётной записи, принадлежащей аккаунту. Административный MQTT superuser сохраняет полный доступ; обычные административно созданные MQTT-пользователи не получают чужое пространство через `#`.

## Обновление существующей установки

Миграции добавляют отдельные аккаунты и nullable-связи владельца. Прежние администраторы, MQTT-пользователи и сообщения остаются административными; их автоматическое назначение новым аккаунтам не выполняется.

Префикс `accounts/` резервируется для аккаунтов. До обновления проверьте, что прежние обычные MQTT-клиенты не используют его для своих топиков. Для административной панели и пользовательского кабинета используются отдельные учётные записи.

Обновляйте схему и бинарник обычной процедурой развёртывания с возможностью восстановления. Регистрацию включайте явно после проверки HTTPS и выбора общего лимита аккаунтов.

### Переход с прежних MQTT-имён аккаунтов

Новые префиксы имеют формат `accounts/<логин>/`, MQTT-логины учётных записей – `<логин>.<название учётной записи>`. Для установки с прежними UUID-префиксами сначала сохраните и проверьте резервную копию. Остановите брокер и выполните новым бинарником с его обычным закрытым окружением:

```bash
clex-mqtt accounts upgrade-names --reset-mqtt-state
```

Команда выполняет переход одной транзакцией: сохраняет аккаунты, MQTT-пароли и идентификаторы учётных записей, обновляет MQTT-логины и правила доступа. Старые MQTT-сессии аккаунтов, их подписки, очереди и старые сообщения, включая Retain и Will, сбрасываются. MQTT-пользователи без владельца сохраняются. При конфликте логина или ссылках на старые сообщения из другого клиента либо моста переход отменяется целиком. Работающий брокер блокирует выполнение команды. Новый сервер отказывается запускаться с прежними MQTT-именами аккаунтов до завершения перехода. Повторный запуск после успешного перехода не сбрасывает новое состояние.

После запуска брокера обновите MQTT-логин и топики на устройствах по данным кабинета. Пароли MQTT-учётных записей и Client ID можно сохранить. Схема БД и контрольные суммы прежних миграций не изменяются.

## Локальная проверка

Полный набор:

```bash
python3 scripts/check.py
```

Реальный браузер, API и MQTT:

```bash
npm run test:accounts-ui
```

Проверка запускает отдельный loopback-брокер и временную схему в `TEST_DATABASE_URL`, создаёт одноразового администратора и удаляет схему после завершения. Chromium берётся из игнорируемого `.cache/playwright`, временный профиль находится в кэше проекта. При необходимости установите браузер в проект:

```bash
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/playwright" npx playwright install chromium --only-shell
```

Проверяются регистрация, CRUD MQTT-учётных записей, изоляция API/MQTT, сообщения и Retain, квоты, адресная блокировка, сброс пароля и отсутствие переполнения desktop/mobile. Скриншоты сохраняются в игнорируемом `work/accounts-ui`.

Логотип административной панели возвращает в «Обзор», логотип личного кабинета – к MQTT-доступу. Явная ссылка «На главную» на страницах входа открывает публичную главную.
