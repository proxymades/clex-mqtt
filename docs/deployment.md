# Развёртывание CLEX MQTT

Для нового VPS сначала выполните [подготовку Ubuntu 24.04, DNS и SSH-доступа](ubuntu-vps.md).

Брокер – отдельный процесс со встроенными файлами панели и отдельной базой PostgreSQL. Во время работы Node.js не требуется. При размещении на сервере с другими сервисами учитывайте их потребление памяти, соединений и дисковых ресурсов.

Документ содержит инструкции и шаблоны Docker Compose, systemd и nginx. Перед production требуется проверка целевой конфигурации на отдельном Linux staging-сервере, включая TLS, восстановление БД и перезапуск процесса. Функции брокера описаны в разделе [«Возможности»](features.md).

## Локальная разработка с установленным PostgreSQL

Целевое окружение БД – PostgreSQL 17. Node.js 22.21.1 собирает панель, Rust 1.93.1 собирает брокер. Используйте версии из конфигурации проекта и lock-файлы.

Если локальный PostgreSQL уже установлен, запустите его обычным способом. Скрипт подготовки подключается через локальный Unix socket и требует роли с правами создания выделенной роли и четырёх новых баз:

```bash
python3 scripts/local_setup.py
npm ci
npm run ui:build
cargo run --locked -- migrate
python3 scripts/bootstrap_admin.py
cargo run --locked -- serve
```

Скрипт создаёт только выделенные базы `clex_mqtt_dev`, `clex_mqtt_test`, `clex_mqtt_codegen`, `clex_mqtt_shadow`. При обнаружении существующей конфигурации он не сбрасывает пароли. Файл `.env` содержит локальные учётные данные, создаётся с правами `0600` и исключён из Git. Пароль локальной панели находится в `CLEX_ADMIN_PASSWORD` этого файла. Не публикуйте его и не переносите локальный `.env` в production.

Панель доступна по `http://127.0.0.1:8085`, MQTT TCP – `127.0.0.1:1883`, MQTT WebSocket – `ws://127.0.0.1:8085/mqtt` с WebSocket subprotocol `mqtt`. Проверка готовности: `GET /health/ready`; проверка существования HTTP-процесса: `GET /health/live`.

Проверки проекта используют отдельную тестовую БД:

```bash
python3 scripts/check.py
```

Не указывайте рабочую базу в `TEST_DATABASE_URL`. Интеграционные проверки создают и удаляют собственные случайные схемы только в выделенной тестовой БД.

## Лицензии при распространении

При передаче собранного бинарника сохраняйте рядом файлы `LICENSE`, `THIRD_PARTY_NOTICES.md` и каталог `third-party` из той же версии исходников. Они содержат условия использования собственного кода и уведомления зависимостей. Docker-образ включает этот комплект в `/usr/share/doc/clex-mqtt`.

Перечень библиотек включает зависимости сборки и поддерживаемых платформ. Лицензии внешних сервисов мониторинга и PostgreSQL применяются к соответствующим самостоятельным компонентам.

## Метрики Prometheus

Задайте случайный `CLEX_METRICS_TOKEN` в закрытом окружении сервиса. Для локальной `.env` используйте `python3 scripts/metrics_token.py`. Экспорт работает по HTTP-пути `/metrics` с отдельным Bearer-токеном. Шаблон Nginx закрывает этот путь на публичном домене; Prometheus обращается к loopback-интерфейсу либо выделенному приватному маршруту. Для удалённого сбора используйте HTTPS и приватный сетевой доступ.

Примеры: `deploy/prometheus/prometheus.yml` и `deploy/prometheus/clex-mqtt-alerts.yml`. Поместите токен в файл секретов Prometheus, укажите доступный ему target и подключите правила после проверки `promtool`. Полный перечень метрик и границы кеша: [monitoring.md](monitoring.md).

Команда `npm run bench:mqtt` выполняет изолированный замер в отдельной тестовой БД. Для подготовки production-профиля запускайте стенд на staging-узле и сохраняйте параметры нагрузки вместе с результатами. Стенд и проверки жизненного цикла используют общую защиту владения внутри тестовой БД; выполняйте их последовательно.

## Защита входа и журнал

Вход в панель ограничен десятью запросами на IP за 60 секунд. Лимит включает успешные и неуспешные попытки; исчерпание возвращает HTTP 429 с `Retry-After`. Одновременно выполняется до четырёх проверок пароля, при занятости возвращается 429. Счётчики находятся в памяти и сбрасываются при перезапуске процесса. Смена имени пользователя не обходит ограничение адреса.

Для локального Nginx задайте `CLEX_HTTP_TRUSTED_PROXY_IPS=127.0.0.1,::1` в закрытом EnvironmentFile. Nginx должен перезаписывать заголовок: `proxy_set_header X-Real-IP $remote_addr;`. Указываются только точные адреса доверенного прокси, до 16 значений через запятую. По умолчанию список пуст: используется адрес TCP-соединения, заголовки клиента игнорируются. От доверенного прокси требуется единственный корректный IP в `X-Real-IP`; `X-Forwarded-For` не участвует в ограничении входа. Для существующей установки добавьте настройку явно и перезапустите службу после проверки конфига прокси.

В «Журнале действий» доступны успешные входы, отказы и ограничения с временем, IP, введённым именем и причиной. Пароли, хеши, cookie и токены не записываются. API возвращает одинаковую ошибку для неверного пароля и неизвестного администратора. Запросы с некорректным JSON или неверным заголовком доверенного прокси отклоняются до проверки учётных данных и не образуют событие входа.

За минуту записывается до 120 событий отказа/ограничения на процесс. Для исчерпанного лимита адреса записывается первое срабатывание в окне; повторные ответы 429 могут отсутствовать в истории. Успешные входы записываются независимо от этого бюджета. Ошибка записи отказа отмечается предупреждением сервиса; ошибка транзакции успешного входа не выдаёт сессию.

События входа хранятся до 30 дней и до 10 000 последних записей. Очистка выполняется при входах и чтении журнала, не чаще раза в минуту; между очистками число строк может временно превышать лимит, а без активности устаревшие строки остаются до следующей очистки. Остальные административные действия этой очисткой не удаляются. Перезапуск сбрасывает счётчики ограничений, сохраняя записанную историю.

`GET /api/v1/audit` требует административную сессию и возвращает массив событий. Параметры: `limit` (1-100, по умолчанию 100), `before` (ID, события строго старше), `search` (имя, код действия или объект), `ip` (точный адрес), `result` (`success`, `failed`, `limited`). В панели используются страницы по 50 записей. Поля `ip`, `result`, `reason` могут быть пустыми у прежних событий и обычных административных действий.

## Ключ и подключения мостов

Для паролей мостов задайте постоянный `CLEX_BRIDGE_SECRET_KEY`: 32 криптографически случайных байта в Base64. Для локального `.env` доступна команда `python3 scripts/bridge_key.py`; существующее значение сохраняется. В production разместите ключ в используемом хранилище секретов или закрытом EnvironmentFile и предоставьте его процессу брокера. Храните ключ отдельно вместе с резервными копиями БД и сохраняйте значение при переносе сервиса. Новый случайный ключ потребует повторного назначения паролей мостов.

Исходящие подключения используют `mqtt://` или `mqtts://` и отдельную учётную запись удалённого MQTT 5 брокера. Разрешите ей публикацию и подписку только в заданных правилами топиках. Для внешних сетей используйте TLS. Проверка сертификата выполняется по системным CA; собственный открытый CA можно добавить в форме моста. Удалённый Client ID автоматически имеет вид `clex-bridge-<UUID>`; постоянная сессия запрашивается на 24 часа, а квоты и фактическое время хранения определяет принимающий брокер.

Каждый активный мост сохраняет исходящую очередь с лимитами `CLEX_MAX_PENDING` и `CLEX_MAX_PENDING_BYTES`. Заполненная очередь отклоняет новые подходящие публикации с сохранением общей транзакционной границы. Отключённый мост сохраняет текущую очередь до включения; редактирование сохраняет уже назначенные топики, удаление очищает очередь. Состояние и причины повторных попыток отображаются в панели. Для смены сервера или логина назначьте пароль нового подключения явно.

Проверка: `npm run test:bridges` использует только отдельную тестовую БД и loopback-порты. Для staging дополнительно проверьте правила доступа, доверие TLS, обрыв сети, заполнение очереди, восстановление БД вместе с ключом и повторную доставку команд на приложении-получателе.

## Необязательный локальный стек Docker Compose

Compose предназначен только для разработки. Он поднимает собственный PostgreSQL 17 и брокер, публикует порты брокера только на `127.0.0.1`. PostgreSQL не имеет опубликованного host-порта. Том `postgres_data` хранит данные между перезапусками.

В закрытый `.env` добавьте следующие переменные, заменив заполнители новыми локальными значениями:

```dotenv
CLEX_COMPOSE_DB_USER=COMPOSE_DATABASE_USER
CLEX_COMPOSE_DB_PASSWORD=COMPOSE_DATABASE_PASSWORD
CLEX_COMPOSE_DB_NAME=clex_mqtt_compose_dev
CLEX_COMPOSE_DATABASE_URL=postgresql://COMPOSE_DATABASE_USER:PASSWORD@postgres:5432/clex_mqtt_compose_dev
```

`CLEX_COMPOSE_DATABASE_URL` должен соответствовать трём отдельным переменным PostgreSQL. Специальные символы пароля в URL требуют percent encoding. Используйте отдельную базу разработки, не связанную с данными других приложений. Compose передаёт приложению только перечисленные в YAML параметры, а не весь локальный `.env`.

Команды выполняются из корня репозитория:

```bash
docker compose --env-file .env -f deploy/compose.yaml build
docker compose --env-file .env -f deploy/compose.yaml up -d --wait postgres
docker compose --env-file .env -f deploy/compose.yaml --profile tools run --rm migrate
```

Миграции запускаются явно до приложения. Затем создайте администратора через stdin. Пример ниже рассчитан на Bash: ввод пароля скрыт, пароль не передаётся аргументом процесса.

```bash
read -r -s -p 'Пароль администратора: ' CLEX_PANEL_PASSWORD
printf '\n'
printf '%s\n' "$CLEX_PANEL_PASSWORD" | docker compose --env-file .env -f deploy/compose.yaml run --rm -T app admin create --username admin --password-stdin
unset CLEX_PANEL_PASSWORD
docker compose --env-file .env -f deploy/compose.yaml up -d app
curl --fail http://127.0.0.1:8085/health/ready
```

Если локальный бинарный брокер уже использует порты 1883/8085, остановите именно его либо выберите другие host-порты в локальной копии Compose. Не используйте `down -v` для обычной остановки: этот флаг удаляет том БД. Для остановки с сохранением данных:

```bash
docker compose --env-file .env -f deploy/compose.yaml down
```

Dockerfile использует отдельные стадии Node и Rust, затем непривилегированный Debian runtime. Панель и официально сгенерированные миграции встроены в бинарный файл. `.env`, сертификаты и закрытые ключи не копируются ни одной инструкцией `COPY`; корневой `.dockerignore` исключает их также из build context. Сборка использует `npm ci` и `cargo build --release --locked`. Для production дополнительно зафиксируйте проверенные digest базовых образов в своей процедуре выпуска.

## Клиентские сертификаты MQTT

Обычный TLS-порт использует `CLEX_TLS_ADDR`, `CLEX_TLS_CERT_FILE`, `CLEX_TLS_KEY_FILE`. Для mTLS дополнительно задайте:

```dotenv
CLEX_TLS_CLIENT_AUTH=optional
CLEX_TLS_CLIENT_CA_FILE=/etc/clex-mqtt/certs/client-ca.pem
```

`optional` разрешает обычные MQTT-подключения и проверяет сертификат, когда клиент его предъявляет. `required` требует клиентский сертификат у каждого TLS-подключения. `none` включает обычный TLS с серверным сертификатом. Для режимов проверки клиента требуется открытый CA bundle; private key выпускающего CA хранится отдельно от брокера. Параметры применяются при запуске сервиса.

У MQTT-пользователя откройте «Сертификаты клиента», загрузите открытый leaf-сертификат PEM с назначением clientAuth и включите «Требовать сертификат клиента», если этот способ обязателен для пользователя. Клиент настраивается с сертификатом, его закрытым ключом и CA для проверки сертификата сервера. При входе только по сертификату MQTT-логин берётся из зарегистрированной привязки. Если клиент передаёт логин, пароль или SCRAM, они должны соответствовать той же учётной записи.

Сначала добавляйте новый сертификат для ротации, затем переключайте клиент и отключайте старый. Удаление и отключение сертификата закрывают только использующие его соединения. Панель показывает срок действия и отпечаток; истёкшие сертификаты завершают работу. За одним пользователем можно закрепить до 16 сертификатов.

Для mTLS используется прямой MQTT TLS-порт либо TCP-прокси с TLS passthrough. HTTP-заголовки reverse proxy в этом механизме не участвуют. Для внешних подключений клиент проверяет CA и имя сервера. Сертификаты и ключи монтируются из закрытого каталога; они исключены из Git и build context.

Для локальной автоматической проверки выполните `npm run test:mtls`. Требуются OpenSSL и отдельный `TEST_DATABASE_URL`; тест создаёт собственные временные ключи, схему и процесс брокера.

## Staging и production на Linux

Первый production-вариант – отдельный systemd-сервис, PostgreSQL 17 и HTTPS reverse proxy nginx. Compose development-конфигурация не является production-конфигурацией: в ней HTTP слушает контейнерный интерфейс и выключены Secure cookies.

Соберите выпуск на Linux нужной архитектуры с Rust 1.93.1 и Node.js 22.21.1:

```bash
npm ci
npm run ui:build
cargo build --release --locked
```

Бинарный файл, собранный на macOS, не запускается на Linux. На staging проверьте артефакт именно для целевой архитектуры и совместимого Linux runtime.

Подготовьте отдельного системного пользователя и каталог выпуска. Следующие команды – шаблон для Debian/Ubuntu; выполните их только на выбранном staging/production-сервере:

```bash
sudo useradd --system --user-group --home-dir /nonexistent --no-create-home --shell /usr/sbin/nologin clex-mqtt
sudo install -d -m 0755 /opt/clex-mqtt /opt/clex-mqtt/docs
sudo install -d -m 0750 -o root -g clex-mqtt /etc/clex-mqtt /etc/clex-mqtt/certs
sudo install -m 0755 target/release/clex-mqtt /opt/clex-mqtt/clex-mqtt
sudo install -m 0644 docs/deployment.md /opt/clex-mqtt/docs/deployment.md
sudo install -m 0644 deploy/systemd/clex-mqtt.service /etc/systemd/system/clex-mqtt.service
sudo install -m 0600 .env.production.example /etc/clex-mqtt/clex-mqtt.env
sudoedit /etc/clex-mqtt/clex-mqtt.env
```

Если системный пользователь уже существует, не создавайте его повторно. Замените все заполнители в environment-файле. Пользователь PostgreSQL должен быть отдельным от сайта и не иметь `SUPERUSER`, `CREATEDB` или `CREATEROLE`; его права ограничиваются собственной БД/схемой брокера. Для штатного запуска и отдельного применения миграций используйте проверенную политику прав этой БД. SQL миграций создаёт таблицы в текущей схеме.

Обязательные production-параметры:

```dotenv
CLEX_ENV=production
DATABASE_URL=postgresql://BROKER_DB_USER:PASSWORD@127.0.0.1:5432/clex_mqtt
CLEX_MQTT_ADDR=127.0.0.1:1883
CLEX_HTTP_ADDR=127.0.0.1:8085
CLEX_PUBLIC_URL=https://mqtt.example.com
CLEX_COOKIE_SECURE=true
CLEX_TLS_ADDR=0.0.0.0:8883
CLEX_TLS_CERT_FILE=/etc/clex-mqtt/certs/fullchain.pem
CLEX_TLS_KEY_FILE=/etc/clex-mqtt/certs/privkey.pem
CLEX_DB_MAX_CONNECTIONS=10
CLEX_MAX_PACKET_BYTES=1048576
CLEX_MAX_CONNECTIONS=1000
CLEX_MAX_INFLIGHT=32
CLEX_MAX_PENDING=10000
CLEX_MAX_PENDING_BYTES=67108864
CLEX_SHUTDOWN_TIMEOUT_SECS=10
RUST_LOG=clex_mqtt=info,tower_http=warn
```

Сохраните environment-файл с правами `0600` и владельцем root. Его читает systemd. Сертификат и ключ MQTT TLS должны быть доступны системному пользователю брокера: например, root:clex-mqtt и `0640` для файлов в каталоге `0750`. Подготовьте обновление этих файлов при продлении сертификата; после замены ключа/сертификата нужен проверенный перезапуск брокера. Учитывайте отдельные сертификатные пути nginx и MQTT TLS.

У PostgreSQL оставьте включёнными `fsync`, `full_page_writes` и `synchronous_commit`. Брокер проверяет настройки устойчивой записи; ослабление этих гарантий несовместимо с подтверждением durable сообщений. Нагрузку создают также очистка очередей, WAL, checkpoint и autovacuum. Лимиты памяти и соединений определяются доступными ресурсами сервера и совокупной нагрузкой размещённых сервисов.

До запуска службы примените миграции явно. Команды используют environment-файл systemd и не печатают его содержимое:

```bash
sudo systemctl daemon-reload
sudo systemd-run --quiet --wait --pipe --collect \
  --property=User=clex-mqtt --property=Group=clex-mqtt \
  --property=EnvironmentFile=/etc/clex-mqtt/clex-mqtt.env \
  --property=WorkingDirectory=/opt/clex-mqtt \
  /opt/clex-mqtt/clex-mqtt migrate
```

Создайте администратора через stdin тем же бинарным файлом. Пример для Bash:

```bash
sudo -v
read -r -s -p 'Пароль администратора: ' CLEX_PANEL_PASSWORD
printf '\n'
printf '%s\n' "$CLEX_PANEL_PASSWORD" | sudo systemd-run --quiet --wait --pipe --collect \
  --property=User=clex-mqtt --property=Group=clex-mqtt \
  --property=EnvironmentFile=/etc/clex-mqtt/clex-mqtt.env \
  --property=WorkingDirectory=/opt/clex-mqtt \
  /opt/clex-mqtt/clex-mqtt admin create --username admin --password-stdin
unset CLEX_PANEL_PASSWORD
sudo systemctl enable --now clex-mqtt
curl --fail http://127.0.0.1:8085/health/ready
```

Шаблон службы запускает непривилегированного пользователя и делает файловую систему доступной только для чтения. Брокер не пишет локальные очереди; постоянные данные находятся в PostgreSQL. Логи поступают в journal. Проверяйте сообщения через `journalctl -u clex-mqtt`; не включайте вывод payload, паролей или SQL-параметров в production.

### HTTPS и WebSocket

Подготовьте DNS и действующий сертификат для отдельного имени, например `mqtt.example.com`. В копии `deploy/nginx/clex-mqtt.conf` замените имя и сертификатные пути, затем установите файл в подходящий include-каталог nginx. Добавьте отдельный server-блок, сохранив действующие конфигурации других сервисов.

```bash
sudo nginx -t
sudo systemctl reload nginx
curl --fail https://mqtt.example.com/health/ready
```

Панель использует HTTPS 443, браузерные MQTT-клиенты – `wss://mqtt.example.com/mqtt` с subprotocol `mqtt`. Обычный MQTT TLS использует 8883 непосредственно у брокера; это другой протокол, HTTP reverse proxy его не обслуживает. Порт 1883 и HTTP 8085 остаются loopback. Открывайте на firewall только необходимые публичные порты. Публичный plaintext MQTT требует явного `CLEX_ALLOW_PLAINTEXT_MQTT=true`; предпочтителен TLS.

Для staging проверьте вход/выход администратора, создание MQTT-пользователя и ACL, соединение TLS/WSS, retained, reconnect с persistent session и перезапуск с восстановлением очереди. Дополнительно проверьте поведение при недоступной БД и отказе второго процесса, использующего ту же базу. `GET /health/ready` подтверждает готовность по проверке БД, но не заменяет эти сценарии.

## Обновление, резервная копия и откат

Перед обновлением сохраните предыдущий Linux-бинарный файл, конфигурацию и резервную копию БД. Используйте `pg_dump` совместимой версии в custom format и отдельно храните необходимые роли/права. Передавайте пароль через защищённый passfile или менеджер секретов; не записывайте URL с паролем в shell history. [Локальный механизм копирования](backups.md) сохраняет семь проверенных комплектов с автоматической ротацией и без фиксированного лимита в гигабайтах. Пробное восстановление выполняется на отдельном PostgreSQL. Для восстановления при потере самого VPS нужна дополнительная копия на другом носителе.

Порядок первого варианта обновления:

1. Проверьте новый артефакт и миграции на восстановленной staging-копии БД.
2. Запланируйте остановку клиентов, остановите `clex-mqtt` и завершите финальное резервное копирование.
3. Установите новый бинарный файл, явно выполните его команду `migrate` при остановленном брокере.
4. Запустите службу, проверьте readiness и MQTT reconnect/delivery.

Миграции создаются только официальным Prisma generator. Не переписывайте уже применённые SQL-файлы и не создавайте их вручную. Во время штатного `serve` миграции автоматически не выполняются.

Откат бинарного файла возможен только при совместимости с уже применённой схемой. Если миграция несовместима, остановите сервис и восстановите проверенную резервную копию БД вместе с соответствующим бинарным файлом и конфигурацией. Изменения после момента копии могут быть потеряны. Этот процесс не обещает обновление без простоя или сохранение всех сообщений при восстановлении старого snapshot.

Документация поставщиков: [PostgreSQL WAL и устойчивые commit](https://www.postgresql.org/docs/17/runtime-config-wal.html), [autovacuum](https://www.postgresql.org/docs/17/routine-vacuuming.html), [nginx WebSocket proxy](https://nginx.org/en/docs/http/websocket.html).

## Пользовательские кабинеты

Регистрация отключена по умолчанию. После обновления схемы и бинарника задайте `CLEX_REGISTRATION_ENABLED=true` и подходящий `CLEX_MAX_ACCOUNTS` (по умолчанию 100, диапазон 1-1000). Маршрут `/account` должен проксироваться Nginx к HTTP-сервису вместе с остальной панелью. Квоты, резервируемый префикс `accounts/` и обновление описаны в [accounts.md](accounts.md).

Главная `/` содержит вход в личный кабинет `/account` и ссылку `/account/register`, когда регистрация включена. Административная панель открывается напрямую по `/admin`. Старые ссылки `/#overview`, `/#users` и другие известные административные разделы переводятся на `/admin` с сохранением фильтров в hash. Эти страницы используют общий HTTP-сервис и прежние API авторизации.
