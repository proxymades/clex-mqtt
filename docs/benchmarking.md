# Нагрузочные измерения

## Запуск

```bash
npm run bench:mqtt
npm run bench:mqtt -- --profile standard
npm run bench:mqtt -- --publishers 4 --subscribers 8 --messages 1000 --qos 1 --window 16
npm run bench:mqtt -- --protocol 4 --qos all
```

Набор коротких нагрузок с одинаковым payload и окном издателя:

```bash
npm run bench:mqtt -- --publishers 1 --subscribers 1 --messages 100 --window 8
npm run bench:mqtt -- --publishers 2 --subscribers 2 --messages 250 --window 8
npm run bench:mqtt -- --publishers 4 --subscribers 4 --messages 500 --window 8
```

Это 100, 1000 и 8000 отдельных доставок на каждый QoS. Выполните минимум три повтора каждой версии; для целевого QoS добавьте `--qos 2` и чередуйте исходный и изменённый бинарники через `--binary`. Сравнивайте медиану и диапазон полученных p50/p95/p99 и скоростей. Такое сравнение использует процентили отдельных прогонов, а не объединённое распределение.

По умолчанию используется release-сборка с параметрами `Cargo.toml`. Флаг `--debug` выбирает отладочный бинарник и отмечает этот режим в отчёте. Сборка требует Rust, Node.js, установленных npm-зависимостей и работающего PostgreSQL с утилитой `psql`.

`--binary work/benchmarks/baseline` выбирает заранее сохранённый бинарник внутри проекта и пропускает сборку. `binarySha256` в отчёте позволяет сверить исполняемый файл. Для сравнения сохраните исходный бинарник после release-сборки и запускайте обе версии одним стендом.

Контроль метрики доставки: `--publishers 1 --subscribers 1 --messages 20 --qos 2 --subscriber-pause-ms 1000`. Стенд на секунду приостанавливает чтение сокета подписчика. Подтверждения издателю продолжаются, а `deliveryLatencyMs` включает ожидание подписчика. `subscriberPauseMs` записывается в отчёт; для обычных сравнений используется 0.

`TEST_DATABASE_URL` должна указывать на отдельную loopback-БД со словом `test` в имени. Стенд создаёт только свою случайную схему `benchmark_<UUID>`, применяет встроенные миграции, создаёт временные административные и MQTT-учётные данные, запускает отдельный процесс и освобождает схему после его остановки. Порты выбираются автоматически. Адрес тестовой БД берётся из локальной конфигурации; процесс измерения получает отдельное окружение. Запускайте стенд и полные проверки проекта последовательно: реальные процессы в одной тестовой БД используют общую защиту владения брокером.

| Профиль | Издатели | Подписчики | Сообщений на издателя | Payload | Окно издателя |
|---|---:|---:|---:|---:|---:|
| `quick` | 2 | 2 | 250 | 256 байт | 8 |
| `standard` | 8 | 8 | 1000 | 256 байт | 16 |

Каждый профиль запускается для QoS 0, 1 и 2; `--qos` выбирает отдельный уровень. `--protocol 5` использует MQTT 5, `--protocol 4` – MQTT 3.1.1. Подписки обычные: каждый подписчик получает все сообщения каждого издателя. Издатель держит до `--window` незавершённых операций. Для брокера заданы 10 соединений PostgreSQL, Receive Maximum до 128, квота 10 000 сообщений и 64 МиБ на очередь. Нагрузка, превышающая эти квоты, проверяется как отказ, а параметры доступны в коде стенда.

Пределы генератора: 32 издателя, 32 подписчика, до 200 000 публикаций и 2 000 000 ожидаемых доставок на уровень QoS; payload 32-65 536 байт, окно 1-128. `--timeout` задаёт срок одного профиля в секундах, включая подключения, публикации и ожидание доставок: по умолчанию 120 для `quick` и 600 для `standard`. Процессы завершает также обработчик прерывания. Отчёты сохраняются в игнорируемую папку `work/benchmarks/<UTC>-<id>/`. При ошибке `failedProfile` сохраняет частичные счётчики отправленных, завершённых и недостающих доставок.

## Равномерная подача

Параметр `--publish-rate 10` задаёт целевой суммарный темп десять публикаций в секунду для всех издателей. Значение по умолчанию `0` сохраняет отправку без искусственной паузы. Поле `publishRate` записывается в каждый профиль отчёта. Таймаут должен покрывать время отправки всего профиля с выбранным темпом.

```bash
npm run bench:mqtt -- --publishers 1 --subscribers 2 --messages 100 --window 1 --publish-rate 10 --timeout 60
```

Ожидание запланированного момента отправки происходит до записи timestamp в payload. Поэтому `deliveryLatencyMs` измеряет путь от фактической отправки до получения, а не интервал ожидания генератора. Параметр задаёт целевой темп; точность таймеров и занятость генератора влияют на фактическое расписание. Равномерный профиль измеряет задержку при выбранной частоте, пакетный – обработку быстро поданной пачки.

## Что измеряется

- `published`, `expectedDeliveries`, `received`, `missing` – публикации и отдельные доставки всем подписчикам.
- `duplicates`, `corrupt`, `reordered` – повторные уникальные идентификаторы, нарушение двоичного payload и нарушение порядка одного издателя у одного подписчика.
- `publishCompletionPerSecond` – завершённые клиентом операции публикации в секунду. Для QoS 0 завершение означает запись клиентом, для QoS 1 – PUBACK, для QoS 2 – PUBCOMP.
- `deliveredPerSecond` – уникальные полученные сообщения, делённые на время от начала публикаций до завершения и публикаций, и всех доставок.
- `deliveryLatencyMs` – p50/p95/p99 и границы от передачи публикации MQTT.js до события `message` у подписчика. Время кодируется в самом двоичном payload и измеряется монотонными часами одного процесса генератора.
- `publishCompletionLatencyMs`, `connectionLatencyMs` – распределения клиентских завершений публикации и подключения.
- `sampledPeakRssMiB`, `cpuSeconds`, `averageCpuPercent` – выборочный пик RSS и CPU только процесса брокера, с периодом 250 мс. На Linux используются тики CPU и RSS из `/proc/<pid>/stat`; на других системах используется `ps`. CPU 100% соответствует одному занятому ядру. Поля с отсутствующим измерением имеют значение `null`.
- `deliveriesPerSubscriber` – число уникальных проверенных payload у каждого подписчика.
- `diagnostics` – выборочный максимум очереди, максимумы её фаз, остаток после закрытия клиентов и CPU соединений PostgreSQL, принадлежащих тестовому брокеру. Период снимков – 500 мс плюс время сбора. CPU PostgreSQL относится к прикладным backend-процессам; WAL writer, checkpointer и другие общие процессы учитываются на уровне сервера отдельно.

`diagnostics.json` сохраняет временной ряд фаз очередей, объём, входящий QoS 2 и категории запросов/ожиданий собственных соединений PostgreSQL. Сбор выполняется read-only запросами в тестовой схеме с таймаутом 1500 мс. При очереди от 1000 и 6000 элементов стенд сохраняет `EXPLAIN (ANALYZE, BUFFERS)` диагностических SELECT для квоты, резервирований, выборки payload и поиска истёкших сообщений. Планы отражают указанный момент и конкретный SELECT; подготовленные запросы брокера могут использовать другой план. Сопоставляйте их с активностью и счётчиками транзакций. Выборочные максимумы могут пропускать короткие пики.

Число сообщений проверяется отдельно у каждого подписчика, каждый payload содержит идентификатор запуска, издателя, номер, timestamp и контрольный образец байтов. Нарушение целостности, пропуск, перестановка или ошибка соединения завершает измерение с ошибкой. Повторы QoS 1 учитываются отдельным показателем. Генератор завершает профиль после получения ожидаемого количества и короткого интервала для учёта последних повторов.

## Трассировка этапов

Флаг `--trace` включает ограниченный сбор для тестовых топиков и сохраняет `trace.json` с правами `0600` в закрытом каталоге прогона. Файл содержит страницу диагностики и подробные события доступных публикаций без payload. Для полного набора используйте до 100 публикаций на прогон; более длинный тест вытесняет ранние записи согласно ёмкости диагностики.

Сопоставляйте `session_locked`, `bridge_routing`, `subscription_match`, `queue_prepared`, `committed` и события получателя. Время до `session_locked` включает получение транзакции и блокировки; интервал после `committed` показывает дальнейшую подготовку и доставку. Метрики ожидания хранилища суммируются по операциям и могут превышать длительность прогона из-за параллельных ожиданий. Сбор трасс влияет на нагрузку, поэтому для сравнения производительности выполняйте также прогоны без него.

## Сравнение

Для схем с учётом квот каждый снимок дополнительно сравнивает известные агрегаты сессий с независимым расчётом по исходным сообщениям. `accountingAuditedSamples` показывает число проверенных снимков, `accountingMismatchSamples` – число снимков с расхождением. `accountingUnknown` в исходном ряду показывает агрегаты, ожидающие первого пересчёта после старта. Проверка доступна и при сравнении с более ранним бинарником: его схема получает пропуск аудита агрегатов. Ошибка сбора диагностики или расхождение завершают стенд с ошибкой и сохраняют частичный отчёт.

Начало обмена следует за подключением клиентов и подтверждением подписок. Длительность обмена включает прогрев маршрутов выбранного профиля; подключения имеют отдельные показатели. Все профили идут в одной временной схеме, по порядку QoS 0, 1, 2. Для сравнения изменений используйте одинаковые аргументы, режим сборки, настройки PostgreSQL и стабильную фоновую нагрузку. Сохраняйте несколько повторов и сравнивайте распределение.

Результат относится к полному пути: генератор MQTT.js, loopback TCP, брокер, PostgreSQL с fsync и обратная доставка. Генератор и PostgreSQL также используют ресурсы компьютера. Возможности production-узла оцениваются отдельным длительным испытанием с целевой сетью, TLS, числом клиентов и профилем подписок. `report.json` содержит параметры конкретного замера, а `metrics.openmetrics` – агрегаты экспортера после обмена; персональные данные и секреты остаются в окружении временного процесса.
